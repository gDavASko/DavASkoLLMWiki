# Анализ архитектурных подходов: Классический RLM vs ReDel (Подход "Сотрудников")

В этом документе проводится сравнение двух исходных реализаций Recursive Language Models из нашего ресёрча:
1. **Классический RLM (MIT OASYS Lab)** — основан на выполнении программного кода (REPL).
2. **ReDel (Recursive Delegation)** — подход, где "Root-агент" делегирует задачи "Sub-агентам" (сотрудникам) через вызов инструментов (Tool Calling).

## 1. Классический RLM (Подход MIT)

### Принцип работы
LLM получает контекст (в виде переменной в REPL) и генерирует **сырой код** (например, на Python или JavaScript). Среда выполняет этот код (`eval`/`exec`) и возвращает `stdout` обратно в LLM. Если код содержит вызов `sub_rlm("prompt")`, среда запускает отдельную LLM для этой подзадачи.

### Плюсы
- **Максимальная гибкость:** LLM может писать любые алгоритмы (циклы `for`, фильтрации, математику).
- **Манипуляция данными:** Идеально для квадратичных задач (сравнить все пары `O(N^2)`).

### Минусы
- **Требования к модели:** Модель должна **идеально** писать код без синтаксических ошибок. Локальные модели (7B-14B) часто ошибаются в синтаксисе при длинных генерациях.
- **Безопасность и стабильность:** Выполнение сырого `eval()` сгенерированного кода может уронить процесс из-за бесконечных циклов или утечек памяти.
- **Сложность отладки:** Код генерируется на лету, отследить логику сложнее.

## 2. ReDel (Подход делегирования / "Сотрудники")

### Принцип работы
Вместо написания сырого кода, Root-модель использует **Tool Calling (вызов функций)**. У неё есть инструмент `delegate_task(task_description, context_chunks)`. Модель передаёт нужные куски данных и инструкцию "Сотруднику" (Sub-агенту). Тот выполняет задачу и возвращает готовый ответ.

### Плюсы
- **Надёжность для локальных моделей:** Форматировать JSON для вызова инструмента (`delegate_task`) гораздо проще, чем писать безошибочный цикл `for` на JavaScript. С этим справятся даже локальные Qwen2.5-Coder 7B или Llama-3-8B.
- **Структурированность:** Логика вызовов выглядит как дерево задач, что легко визуализировать и дебажить (у ReDel есть готовый Web UI).
- **Безопасность:** Нет `eval()`. Модель просто вызывает предопределённые функции.

### Минусы
- **Меньше алгоритмической свободы:** Модель ограничена предоставленными инструментами. Написать кастомную математическую агрегацию сложнее.

## 3. Вывод: Что лучше подходит для DavASkoLLMWiki?

### Рекомендация: **Подход на базе ReDel (Делегирование)**

Учитывая ваши требования:
1. **Интеграция в экосистему Node.js** (DavASkoLLMWiki написан на JS).
2. **Возможность запуска локальной LLM** (полностью локальный движок).

**Почему ReDel лучше:**
Заставить локальную 8B модель стабильно генерировать валидный JavaScript код для `vm.runInContext` в цикле (Классический RLM) — невероятно сложная задача. Модели будут галлюцинировать с синтаксисом. 
А вот научить локальную модель вызывать один чёткий инструмент `spawn_worker(prompt, context_id)` — легко. Современные локальные модели (даже небольшие) отлично обучены на Tool Calling (структурированный JSON).

### Предлагаемая архитектура движка:
1. **Root Agent (Менеджер):** Анализирует общий запрос пользователя и принимает решение, как разбить базу знаний. Он может выбрать один из инструментов:
   - `search_wiki(query)` — обычный быстрый RAG (если запрос простой).
   - `spawn_worker(sub_prompt, data_layer)` — запускает "Сотрудника" для анализа целого слоя или конкретных файлов.
2. **Worker Agent (Сотрудник):** Получает узкую задачу от Менеджера и массив текста. Он анализирует его (возможно, рекурсивно разбивая дальше) и возвращает саммари.

Эта архитектура позволяет нам:
- Легко переключаться между внешними API и локальной Ollama (все они поддерживают Tool Calling).
- Избежать опасного `eval()` кода на проде.
- Полностью контролировать глубину погружения.
