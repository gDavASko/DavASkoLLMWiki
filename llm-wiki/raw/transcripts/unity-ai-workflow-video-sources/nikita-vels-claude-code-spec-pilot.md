## 1. Контекст, Проблема и Стек

* **Решаемая проблема:** 
  * При работе с ИИ-кодерами (такими как `Claude Code`) без четкой структуры запросов контекст быстро забивается избыточной информацией («кашей»), что приводит к ухудшению ответов и перерасходу токенов.
  * Самая частая и дорогая ошибка — запуск параллельных субагентов до согласования технического плана (спецификации). В результате субагенты начинают додумывать детали («галлюцинировать»), их решения расходятся, а лимит токенов сгорает впустую.
  * Разработчики часто тратят время на избыточные диалоги при тривиальных правках или, напротив, доверяют ИИ критические, необратимые операции (деплой, транзакции, удаление данных).
* **Технологический стек:** 
  * ИИ-кодеры (`Claude Code` / `Claude 3.5 Sonnet / Opus`), фреймворки субагентов (Agent Teams), инструменты MCP (Model Context Protocol), Skill Validator, Browser Automation.
* **Критерии выбора:** 
  * Данная стратегия заменяет хрупкий Prompt Engineering на строгий программно-ориентированный конвейер («хребет» из 4 обязательных шагов и 2 продвинутых шагов), который экономит до 40% лимита токенов и ускоряет сборку в 3-5 раз.

## 2. Архитектура и Концептуальная модель

Архитектура Spec Kit базируется на детерминированном переходе между шагами сборки ПО. ИИ-кодер выступает в роли исполнителя, строго ведомого рамками обвязки (Harness) и обратной связью от разработчика.

### Диаграмма конвейера сборки (Backbone)

```
 [Входная задача] 
        │
        ▼
 1. INTERVIEW ME  ◄──── (Сбор ТЗ, шкалирование масштаба)
        │
        ▼
 2. WRITE ME A SPEC ◄── (Составление спеки)
        │
        ├──────────────────────────┐
 [Пользователь говорит "Да"]  [Пользователь говорит "Нет" / Правки]
        │                          │
        ▼                          ▼
 3. LAUNCH SUB AGENTS        Возврат на Шаг 1 / Шаг 2
 (Параллельная сборка)
        │
        ▼
 4. VERIFY BEFORE BUILD ◄── (Самопроверка ИИ + Линтеры/Тесты)
        │
        ▼
   [Готовая фича] ────► [Ручной контроль разработчиком (Human-in-the-Loop)]
```

## 3. Пошаговый гайд по реализации (6 фраз Spec Kit)

### Шаг 1: `interview me` (Интервьюирование)
ИИ задает точечные вопросы разработчику для прояснения неопределенности. Это исключает догадки со стороны модели.
* **Количество вопросов:** Ограничено масштабом задачи. На средних задачах рекомендуется задавать не более 3 вопросов, на крупных — по мере необходимости.
* **Если разработчик не знает решения:** Он явно пишет: *«Я не знаю, как это реализовать, предложи свое решение»*.

### Шаг 2: `write me a spec` (Спецификация)
Формирование технического плана реализации (Implementation Spec) на основе ответов из интервью.
* Спецификация должна содержать:
  * Цель и архитектурные решения.
  * Список изменяемых/создаваемых файлов.
  * Функционал и сценарий работы.
  * Критерий готовности (DoD).
* **⛔ КРИТИЧЕСКИЙ БАРЬЕР:** ИИ категорически запрещено переходить к сборке или запускать параллельных агентов, пока пользователь явно не подтвердил спецификацию словом **«Да»** (или аналогичным утвердительным ответом).

### Шаг 3: `launch sub agents` (Запуск субагентов)
Делегирование отдельных кусков утвержденной спецификации параллельным субагентам.
* **Инструменты:** Встроенные задачи (`Task`) или экспериментальные мультисессионные команды (`Agent Teams`).
* **Правило:** Каждый субагент получает изолированный контекст, промпт и права только на свою подзадачу, строго следуя общей утвержденной спеке.
* **Фоллбэк:** При исчерпании лимитов на Pro-тарифах выполнение продолжается последовательно по спеке.

### Шаг 4: `verify before you build` / `verify before handoff` (Верификация)
Многослойный процесс проверки работоспособности кода перед демонстрацией пользователю.
* **Три уровня проверки:**
  1. *Правило в `CLAUDE.md`:* Требование к ИИ написать план тестирования до внесения изменений.
  2. *Автопроверка:* Запуск компилятора, линтеров, автотестов или проверка интерфейса через Browser-агента.
  3. *Зона контроля человека:* ИИ приостанавливает работу и просит ручного подтверждения для всех критических зон.

## 4. Продвинутые практики (Этаж выше)

### Шаг 5: `build me a skill` (Упаковка в навык)
Повторяющиеся рутинные правила и цепочки действий упаковываются в переиспользуемые файлы умений (скиллы).
* **Секция `Gotchas` (Грабли):** Обязательный раздел скилла, куда записываются все ошибки, допущенные ИИ в ходе сессии, и ручные исправления разработчика. При повторном запуске скилла ИИ считывает `Gotchas` и не наступает на те же грабли дважды.
* **Правило создания:** Скиллы создаются только на основе реально состоявшегося и успешно отлаженного диалога, а не абстрактного проектирования.

### Шаг 6: `automate this` (Автоматизация)
Решение о полной передаче задачи под контроль автоматических скриптов.
* **Тест на вкус (Taste Test):** Требуется ли субъективная оценка вкуса/стиля для проверки результата?
  * *Да* — использовать только **аугментацию** (ИИ ускоряет работу, но человек находится внутри петли управления).
  * *Нет* (результат измерим численно/логически) — можно переходить к **автоматизации**.
* **Анализ 80/20:** Устроит ли результат, если он будет выполнен хорошо на 80%?
  * *Да* — автоматизировать.
  * *Нет* (критичные процессы: финансы, доступы, биллинг) — только аугментация с обязательным `Human-in-the-Loop`.

## 5. Защитные механизмы и Гарды (Safeguards)

### 🛡️ Гард 1 — Масштаб задачи (Предотвращение overhead)
* **Тривиальный:** 1-2 простых действия (опечатка, переименование, форматирование). Спека и интервью не требуются, код пишется напрямую.
* **Средний:** 1 законченная фича (2-4 неочевидных решения). Интервью $\le$ 3 вопросов $\rightarrow$ спека $\rightarrow$ сборка $\rightarrow$ проверка.
* **Крупный:** Новая подсистема или сложный модуль. Полный конвейер (интервью, спека, субагенты, проверка).

### 🛡️ Гард 2 — Блокировка параллелизации без спеки
* Запрещен запуск любых параллельных воркеров до явного утверждения спецификации.
* **Стоп-фраза:** Если ИИ рванул писать код без согласования плана, разработчик должен использовать команду: **«Стоп, сначала спека»**. ИИ обязан прервать работу и вернуться к шагу 2.

### 🛡️ Гард 3 — Зоны ответственности человека (Human Only)
* ИИ-агентам запрещено самостоятельно выполнять:
  * Проведение транзакций и любые платежные операции.
  * Необратимое удаление данных (`rm -rf`, сброс БД).
  * Прямой деплой/публикацию в прод или `git push --force`.
  * Работу с боевыми API-ключами и конфиденциальными секретами.
