# Loop Engineering: Концепция и применение

**Источник:** [Не будь оператором LLM – освой Loop Engineering с агентами](https://www.youtube.com/watch?v=xcxU2QsddK0)

## Проблема традиционного подхода (Prompt Engineering)
Традиционный метод работы с LLM, когда разработчик вручную пишет промпт, ждёт ответа, анализирует результат и формулирует следующий запрос, не масштабируется. В такой парадигме разработчик действует как оператор LLM, а не как инженер, проектирующий систему. Если время, затрачиваемое на взаимодействие с агентом, превышает время, уделяемое написанию кода или принятию инженерных решений, требуется изменение подхода.

## Концепция Loop Engineering
Loop Engineering — это паттерн проектирования агентских workflow, автоматизирующий взаимодействие с LLM. Разработчик проектирует цикл, который:
1. Автоматически запускает агента.
2. Передаёт ему задачи.
3. Проверяет результаты.
4. Сохраняет состояние работы.
5. Определяет дальнейшие действия.

Паттерн популяризирован Eddie Asmani (Google Cloud AI) и Борисом Чёрным (Anthropic, Cloud Code). Разработчик переходит от написания одиночных промптов к проектированию циклов вокруг модели.

## Архитектура системы
Система разделяется на два уровня циклов:

### Внутренний цикл (LLM)
Базовая работа агента: сбор контекста, анализ, выполнение действий, получение обратной связи, исправление ошибок и продолжение работы.

### Внешний цикл (Оркестратор)
Управляется разработчиком и включает:
- Триггеры и расписание запуска.
- Изоляцию работы агента (среда).
- Декомпозицию задач.
- Управление итерациями.
- Критерии успешного выполнения.
- Лимиты и условия завершения цикла.

## Компоненты Loop Engineering
1. **Automations:** Инструменты запуска цикла по расписанию/событию, парсинг задач и роутинг.
2. **Git Worktrees:** Изолированные рабочие деревья Git для параллельной работы агентов без взаимного влияния (каждый агент имеет свою директорию, HEAD, индекс).
3. **Skills (Навыки):** Компоненты для извлечения багов, работы с таск-трекерами и формирования to-do листов.
4. **Плагины и коннекторы (MCP):** Интеграция с CI/CD, БД, Slack, GitHub, системами мониторинга.
5. **Субагенты (Pattern Maker-Checker):** 
   - **Maker:** пишет код/решение.
   - **Checker:** валидирует результат, запускает тесты, сверяет с архитектурными правилами. Это снижает риск лояльности модели к собственному коду.
6. **Память (State Management):** Внешний источник правды о процессе (Markdown-файлы `plan.md` / `status.md`, тикеты в Jira). Живёт вне контекстного окна LLM и сохраняется между сессиями.

## Родственные практики: Ralph Loop
Ralph Loop — паттерн автономной работы агента, при котором агент выполняет небольшую атомарную задачу, фиксирует изменения, сохраняет состояние и завершает итерацию. Следующая итерация начинается как **новая сессия с чистым контекстом**.
Это критично для предотвращения **Context Rot** (деградации продолжительных сессий из-за переполнения контекстного окна мусором и ошибочными рассуждениями).

## Контракты и Критерии успешности
Для эффективного цикла необходимо:
- **Измеримые цели** (напр., покрытие тестами 80%).
- **Проверяемые критерии** (exit code 0 у npm-тестов, прохождение линтеров).
- **Жесткие границы** (запрет на редактирование определенных файлов или запуск определенных команд).
- **Лимиты** по итерациям, времени или бюджету токенов.
- **Стоп-факторы** для досрочного завершения цикла.

## Матрица зрелости внедрения
1. **Ручной режим:** Промпты и проверка осуществляются человеком.
2. **Парсинг:** Система сама формирует to-do листы из таск-трекеров, код пишет человек.
3. **Изолированный Агент:** Агент пишет код в Git Worktree, человек проверяет Diff и мержит.
4. **Автоматический Checker:** Чекер (отдельный агент/тесты) валидирует PR, человек ставит финальный Approve.
5. **Автономный CI/CD:** Система самостоятельно мержит изменения после успешного прохождения всех проверок. Контроль через алерты.

## Ключевые риски
1. **Токены и бюджет:** Перерасход из-за плохо настроенных лимитов.
2. **Ложное чувство безопасности:** Агент может писать тесты, подтверждающие его же неправильное решение.
3. **Архитектурная деградация:** Локальное решение задачи с нарушением глобального дизайна (дублирование кода, цикличные импорты).
4. **Снижение критического мышления:** Автоматизация не отменяет ответственности инженера.
